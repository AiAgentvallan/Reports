Section 1

What is this? (Plain English)

No jargon. Two audiences covered: non-technical (business) and technical (how it actually works).

💳
Think of it like a credit score for your tenants — before they miss a payment, not after
Non-technical explanation

When a tenant misses a payment, storage facilities usually find out only after it has happened — then they have to chase the tenant, issue warnings, and possibly escalate to a lien or auction process. It's slow, stressful, and costly.

SD already has non-payment automation — when PMS data shows a tenant is delinquent, SD can trigger workflows automatically. This idea adds a layer before that trigger: an AI that watches how tenants behave before they default. Two patterns predict default reliably: (1) payment delays creeping later each month — a tenant who pays on the 3rd, then the 9th, then the 16th is showing a clear trend toward non-payment; and (2) the tenant stops accessing their unit — device telemetry shows they haven't opened or been near their unit in 45+ days, often because they've quietly abandoned it.

The result: a facility manager gets an alert before the tenant misses a payment — "Unit B-05 tenant is showing a high default risk. Payment trend is 12 days later than last month. Unit access has been zero for 6 weeks. Recommended action: call the tenant with a friendly reminder this week." That one call could prevent a months-long delinquency process.

🔑
Why this is unique — SD has data no one else has
The unfair competitive advantage

PMS systems (SiteLink, storEDGE) track payment history — but so do all competitors. What makes SD unique is device telemetry. SD sensors know when a tenant physically accesses their unit. No other self-storage software has this signal combined with payment data.

This is the idea with the highest AI Innovation score (19/20) precisely because it uses a data combination that is exclusive to SD — a genuine competitive moat. Facility managers who use this feature will not want to switch to a competitor who can't offer predictive default detection based on physical access patterns.

The value to SD: this feature makes the Smart Unit subscription stickier and becomes a key reason facility managers add more Smart Units — to get better tenant intelligence coverage. Every new device added at $12/month increases the prediction accuracy for that facility.

👔
How this grows SD revenue — the correct business case
Important: tenant delinquency ≠ SD revenue. Here is the real link.

SD earns $12/device/month flat. Tenant non-payment is the facility manager's revenue problem — not SD's directly. The link to SD revenue works through two paths:

Path 1 — Retention: Facilities that experience recurring delinquency issues blame the platform if they don't get proactive help. This feature makes SD the platform that solves the problem before it becomes a complaint. Happy facility managers stay on SD longer = retained $12/device/month revenue.

Path 2 — Upsell: The quality of this prediction improves with more Smart Units per facility — because more units = more access pattern data = better predictions. Facility managers who see value in the predictive alerts are motivated to add more Smart Units at $12/device to get full facility coverage. This is a direct device expansion driver — same mechanism as Idea #2, but driven by tenant intelligence rather than security coverage.

Step-by-Step Build Plan

7 steps. This is the most technically complex of the 4 ideas — the PMS + telemetry data join in Step 1 is the hardest part. Everything else is straightforward once the data pipeline is clean.

1
Data Layer (Hardest Step)
Join PMS payment data with device telemetry — one row per tenant per facility

This is the most complex data step. The PMS sync tables hold payment history per tenant/unit. The incidents table holds device events per unit. The join key is unit_id — which links a tenant (via PMS) to a specific device (via tod_backoffice). Confirm the exact PMS table names with the backend team before building.

-- Step 1A: Payment delay trend per tenant (last 3 payments) -- How many days later is each payment vs the previous one? WITH payment_history AS ( SELECT c.unit_id, c.tenant_id, c.payment_date, c.due_date, DATE_DIFF(c.payment_date, c.due_date, DAY) AS days_after_due, ROW_NUMBER() OVER (PARTITION BY c.tenant_id ORDER BY c.payment_date DESC) AS payment_rank FROM `tod_backoffice.pms_charges` c -- confirm actual table name WHERE c.charge_type = 'rent' AND c.payment_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 6 MONTH) ) SELECT unit_id, tenant_id, MAX(CASE WHEN payment_rank = 1 THEN days_after_due END) AS latest_delay, MAX(CASE WHEN payment_rank = 2 THEN days_after_due END) AS prev_delay, MAX(CASE WHEN payment_rank = 1 THEN days_after_due END) - MAX(CASE WHEN payment_rank = 2 THEN days_after_due END) AS delay_trend_days, COUNTIF(days_after_due > 0) AS late_payment_count_6mo FROM payment_history GROUP BY unit_id, tenant_id; -- Step 1B: Unit access events from device telemetry (SD-exclusive signal) SELECT d.unit_id, COUNTIF(i.created_at >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)) AS access_last_30d, COUNTIF(i.created_at BETWEEN DATE_SUB(CURRENT_DATE(), INTERVAL 60 DAY) AND DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)) AS access_prev_30d FROM `tod_backoffice.devices` d LEFT JOIN `tod_backoffice.incidents` i ON i.device_id = d.id AND i.sensor_type IN ('motion', 'door') GROUP BY d.unit_id;
⚠️

Confirm before building: Verify the exact PMS charge table name in tod_backoffice with the backend team. Different PMS systems (storEDGE, SiteLink, SSM) may sync into different table schemas. This confirmation is the most critical blocker for this idea.

2
Scoring Engine
Build the Default Risk Scoring Engine — rule-based for v1 pilot

For the 45-day pilot, use a rule-based weighted formula (same approach as Idea #2). This is explainable, fast to build, and easy to validate with the CS team. A true ML model (logistic regression or XGBoost) is a v2 upgrade once outcome data accumulates.

// risk-scorer.js function calculateDefaultRisk(signals) { let score = 0; // Signal 1: Payment delay trend — 0 to 35 points // delay_trend_days = latest payment days late MINUS previous payment days late // Positive = paying later each month = high risk score += Math.min(35, Math.max(0, (signals.delay_trend_days || 0) * 2.5)); // Signal 2: Late payment count (last 6 months) — 0 to 25 points score += Math.min(25, (signals.late_payment_count_6mo || 0) * 8); // Signal 3: Unit access drop (SD-exclusive) — 0 to 25 points // If tenant stopped accessing unit when they previously did = abandonment risk if (signals.access_last_30d === 0 && signals.access_prev_30d > 0) { score += 25; // sudden abandonment } else if (signals.access_last_30d === 0) { score += 12; // generally inactive } else if (signals.access_last_30d < signals.access_prev_30d * 0.3) { score += 8; // access dropped >70% } // Signal 4: Currently delinquent per PMS — 0 or 15 points if (signals.is_currently_delinquent) score += 15; return Math.min(100, Math.round(score)); } // Threshold definitions const RISK_BANDS = { LOW: { min: 0, max: 29, action: 'none' }, MEDIUM: { min: 30, max: 59, action: 'watchlist' }, HIGH: { min: 60, max: 79, action: 'alert_fm' }, CRITICAL: { min: 80, max: 100, action: 'alert_fm_and_cs' } };
3
AI Layer — Claude
Integrate Claude API — write specific intervention for HIGH and CRITICAL risk tenants

Claude is called only for HIGH (60–79) and CRITICAL (80–100) risk tenants. It reads the signal breakdown and writes a specific, professional message for the facility manager explaining why this tenant is flagged and exactly what to do next.

// claude-default-advisor.js async function generateIntervention(tenant, unit, facility, signals, riskScore) { const payload = { unit_number: unit.unit_number, zone: unit.zone_name, risk_score: riskScore, payment_delay_trend: signals.delay_trend_days, // e.g. +12 days later late_payments_6mo: signals.late_payment_count_6mo, access_last_30d: signals.access_last_30d, // e.g. 0 events access_prev_30d: signals.access_prev_30d, // e.g. 8 events is_delinquent: signals.is_currently_delinquent, pms_type: facility.pms_type, next_payment_due_days: signals.days_until_next_due // e.g. 6 days away }; const response = await client.messages.create({ model: "claude-sonnet-4-6", max_tokens: 400, system: [{ type: "text", text: `You are a customer success advisor at Storage Defender. A tenant at a self-storage facility is showing default risk signals. Write a short, specific alert for the facility manager explaining: 1. Which signals are most concerning and why 2. One clear recommended action to take THIS week (before next payment due) Tone: professional, factual, helpful — not alarmist. 2 short paragraphs. Never invent data. Only use what is provided.`, cache_control: { type: "ephemeral" } }], messages: [{ role: "user", content: JSON.stringify(payload, null, 2) }] }); return response.content[0].text; }

6
Feedback Loop
Build outcome tracking — did the flagged tenant actually default?

The feedback loop is what separates this idea from a simple rule engine. After each alert, track the outcome in BigQuery: did the tenant actually default? Was the alert acted on? This data is used to measure precision (how many alerts were correct) and recall (how many defaults were caught). Over time, it powers a true ML model (v2).

Alert fired (HIGH/CRITICAL)
→

→

→

→
Calculate precision/recall
→
Tune signal weights
🤖

v2 upgrade path: Once 3+ months of outcome data accumulates, replace the rule-based scoring with a logistic regression model trained on historical defaults. With enough data, the model learns that "payment delay trend + unit access drop together = 3× stronger predictor than either signal alone." This is when the 19/20 AI Innovation score is truly earned.

7
Testing & Validation
Backtest against historical defaults, validate with CS team, pilot with 5 facilities

Before going live, backtest the scoring formula against known historical defaults — run the algorithm on data from 6 months ago and check how many real defaults it would have caught. This validates the signal weights before any facility manager sees a false positive.

⚠️

False positive risk: This idea has the highest false positive risk of all 4 — a wrong alert tells a facility manager to call a tenant who has done nothing wrong. Agree on an acceptable false positive rate with the CS team before launch (suggested: no more than 1 false alert per facility per week). Adjust the HIGH threshold (currently 60) upward if false positive rate is too high during backtest.

Section 4

Claude AI — Deep Dive

Claude generates the intervention message per at-risk tenant. Called only for HIGH and CRITICAL risk — not for every tenant daily.

🤖

Claude Sonnet 4.6 — Anthropic API

Model ID: claude-sonnet-4-6  |  SDK: @anthropic-ai/sdk  |  Triggered for HIGH (60+) and CRITICAL (80+) risk tenants only
What Claude Does Here
  • Reads the 4 signal values for the specific tenant
  • Identifies which signal is most alarming and why
  • Writes 2 paragraphs: risk explanation + specific action for this week
  • Times the action to the next payment due date
  • Keeps tone factual and non-alarmist — facility managers don't like panic alerts
Why the Access Drop Signal is Unique
  • PMS payment data is available to any competitor
  • SD device telemetry is not — no other platform can detect that a tenant stopped entering their unit
  • Claude can explain this to the FM in plain language: "Unit B-05 had 8 motion events last month. This month: 0. Combined with the payment delay, this suggests the tenant may have stopped using the unit."
  • This explanation is something only SD can give
Cost Estimate (per month)
  • ~5% of tenants reach HIGH+ risk on any given day
  • 200 facilities × avg 50 tenants × 5% = ~500 API calls/day
  • ~400 output tokens per intervention
  • System prompt cached per batch run
  • Estimated: ~$8–12 USD/month for full fleet
What Claude Must NOT Do
  • Must NOT use tenant PII (name, contact details) in the output — use unit number only
  • Must NOT predict probability of default as a % (not enough data in v1)
  • Must NOT suggest legal actions (liens, auctions) — only soft interventions
  • Must NOT invent payment amounts or rental rates — those belong to the PMS
📝 Sample Claude Output — what the facility manager reads in their alert email

"Unit B-05 is showing two concerning patterns together. Their last payment arrived 12 days later than the previous month, continuing a trend that has been moving later for three consecutive months. Additionally, unit access events have dropped to zero in the last 30 days — down from 8 events the previous month. Together, these signals suggest the tenant may be disengaging from the unit.

Recommended action: The next payment for this unit is due in 6 days. A brief, friendly call this week to check in — not about payment — often resolves disengagement early and prevents a missed payment entirely. If the tenant has moved out informally, this is also the right time to confirm unit status."

Section 7

AI Tool Options

The scoring itself is rule-based in v1. Claude generates the intervention narrative. The v2 ML model is optional and longer-term.

⭐ Recommended (v1)
🤖

Claude Sonnet 4.6

Best for generating nuanced, context-aware interventions that combine payment and access signals.

  • Can explain the access drop + payment combo in plain language
  • Triggered-only = ~$8–12/month for full fleet
  • Prompt caching on system prompt
  • SD already has Anthropic account
  • Easy to adjust tone via system prompt
📊

Google BigQuery ML

v2 upgrade: train a logistic regression model directly in BigQuery using outcome data.

  • Native GCP — no external vendor
  • Uses actual default outcomes to train
  • Requires 3+ months of labelled data
  • Replaces rule-based scoring with learned weights
  • Best long-term AI approach for this use case
📋

Rules Only (No AI)

Skip Claude entirely — use templated alert messages based on which signal triggered.

  • Zero AI cost
  • Fastest pilot build
  • Less contextual — misses combined signal nuance
  • Good fallback for first 2 weeks of pilot
  • Add Claude in v1.1 once data pipeline is stable
