Plain English: The "Dark Moment" Problem

Every camera and smart device at a Storage Defender facility talks to a gateway. That gateway is the bridge between your physical security hardware and the cloud. Right now, if a gateway goes completely silent — due to a power cut, internet outage, or someone physically disrupting it — nobody at SD gets automatically notified. The FM only finds out when a tenant calls to say their access doesn't work, or worse, when they arrive at the facility and find a break-in.

The most dangerous moment in storage facility security is not when an alarm goes off — it's the 15-minute window when security silently stops working and nobody knows. A motivated burglar who disables your gateway has a clean runway.

Idea 5 fixes this by turning the gateway's silence into its own alert. Every 60 seconds, a background job asks: "Have we heard from each gateway recently?" If the answer is no for 5+ minutes, the system wakes up, analyzes why it might have gone offline, and sends a smart alert to exactly the right person — with an escalation ladder if nobody responds.

What Triggers This

  • Power cut to the facility
  • Internet/network outage
  • Someone uses a signal jamming device (chammer)
  • Gateway hardware failure or shutdown
  • Physical tampering or disconnection
  • Any event causing loss of cloud communication

What Happens Next

  • Detect silence within 60 seconds
  • Wait 5 minutes to confirm (not a blip)
  • Analyze context: was there motion right before it died?
  • AI classifies the outage type and risk level
  • Alert sent to the assigned Facility Manager
  • Escalate to secondary contacts if no acknowledgment
The user's insight is correct: The gateway already sends heartbeat/communication data. The lastContactedAt field exists today in the SD GraphQL API. This idea is not about building new hardware — it's about listening to data that's already there and acting on it intelligently.

Market Reality Check: Is This Already Done?

Honest answer: basic gateway offline alerts exist in the market. Verkada, Eagle Eye Networks, and Avigilon all send a "device offline" email. But here's what none of them do — and what makes SD's version genuinely novel:

✓ Already Exists in Market (Basic)

  • Verkada: sends email when camera goes offline
  • Eagle Eye: device health dashboard with offline status
  • Avigilon: VMS health alerts for disconnected cameras
  • OpenEye (storage-focused): basic camera offline notification
  • Generic IoT platforms: heartbeat ping + simple alert

★ What SD's Version Adds (Novel)

  • Pre-outage motion burst detection — did someone trigger activity 0–5 min before the gateway died?
  • Jamming pattern recognition — 2+ gateways offline simultaneously = jamming probability score
  • Outage type classification — power cut vs. network vs. jamming vs. hardware failure
  • PMS tenant context — was a high-risk or delinquent tenant in the zone at time of outage?
  • FM assignment + acknowledgment escalation — tracks whether FM responded and escalates to secondary
  • AI-generated narrative — plain English summary of what happened and what to do
The jamming angle is real: RF signal jammers ("chammers") are used in real storage facility break-ins. Attackers block WiFi/cellular frequency to disable cameras before entering. No competitor detects this pattern — they just say "device offline." SD can say "3 gateways at Facility A went offline within 90 seconds of each other at 2:14 AM after motion was detected in Zone C — this looks like a jamming attack."
Verdict: The basic version exists. SD's enhanced version — with pre-outage correlation, jamming detection, PMS cross-reference, and AI classification — is genuinely novel, especially in the self-storage vertical. No direct competitor has this combination.

System Architecture: How It Works

⏱️
Layer 1 — Heartbeat Monitor (Cloud Scheduler + Cloud Run)

Runs every 60 seconds. Queries all active gateways. Flags any where lastContactedAt > 10 minutes ago. Writes initial POSSIBLE_OUTAGE event to BigQuery. Deduplicates so existing outages don't re-trigger.

▼
🔍
Layer 2 — Confirmation Window (5-Minute Hold)

Waits 5 minutes after initial detection, then re-checks. If gateway is back online → mark as recovered, no alert. If still offline → proceed to analysis. This eliminates false alarms from brief network blips (the most common cause of noisy alerts in IoT systems).

▼
📊
Layer 3 — Pre-Outage Context Analyzer (BigQuery)

Queries three data sources for the 10-minute window before loss: (1) motion/incident events from devices in the same zone, (2) simultaneous outage check — are other gateways at this facility also offline?, (3) time-of-day context — after-hours outage is 3× more suspicious than daytime. Builds a context bundle for classification.

▼
🤖
Layer 4 — AI Risk Classifier (Claude Sonnet)

Triggered only for SUSPICIOUS or higher risk (based on pre-outage signals). Receives the full context bundle and outputs: outage type, threat level, plain-English summary, and recommended FM action. Uses prompt caching for the system prompt. Cost: ~$0.02–0.08 per alert. Skipped entirely for NORMAL outages (no AI cost for routine blips).

▼
📣
Layer 5 — Alert Router + Escalation Engine

Routes alert to the FM assigned to the specific gateway (from facility_managers + gateway_assignments). Sends Email (SendGrid) + SMS (Twilio) + Slack. Creates an acknowledgment token with a time window (10 min for CRITICAL, 20 min for ELEVATED). Schedules an escalation check — if no ack within the window, notifies secondary contacts.

Key design decision: The gateway cannot report its own death. If a power cut or jamming device kills it, the gateway can't send an "I'm going offline" message. Detection MUST be cloud-side: "we haven't heard from this gateway in 10 minutes." This is a pull model (cloud polls for silence), not a push model (device reports failure). Most competitors miss this distinction and only support push — meaning they can't detect jamming or power cuts.

Technical Build Plan: Code & Queries

Step 1: Heartbeat Checker — Detect Silent Gateways

// Cloud Run job: runs every 60 seconds via Cloud Scheduler const { BigQuery } = require('@google-cloud/bigquery'); const bq = new BigQuery(); async function checkGatewayHeartbeats() { // Find gateways silent for 10+ minutes, not already flagged in last 30 min const [rows] = await bq.query(` SELECT d.id AS gateway_id, d.facility_id, d.name AS gateway_name, d.last_contacted_at, TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), d.last_contacted_at, MINUTE) AS minutes_silent, f.name AS facility_name, f.timezone FROM \`tod_backoffice.devices\` d JOIN \`tod_backoffice.facilities\` f ON f.id = d.facility_id WHERE d.type = 'gateway' AND d.is_active = TRUE AND d.last_contacted_at < TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 10 MINUTE) AND NOT EXISTS ( SELECT 1 FROM \`sd_monitoring.gateway_outage_events\` e WHERE e.gateway_id = d.id AND e.detected_at > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 MINUTE) AND e.status IN ('CONFIRMED','ALERTING','RECOVERED') ) `); for (const gw of rows) { // Write initial event — status PENDING (5-min confirmation hold) await writeOutageEvent({ gateway_id: gw.gateway_id, facility_id: gw.facility_id, detected_at: new Date().toISOString(), minutes_silent: gw.minutes_silent, status: 'PENDING', facility_name: gw.facility_name, timezone: gw.timezone }); // Schedule confirmation check in 5 minutes await scheduleConfirmation(gw.gateway_id, 5 * 60 * 1000); } }

Step 2: Pre-Outage Context — What Happened Before the Silence?

async function analyzePreOutageContext(gatewayId, facilityId, lossTime) { const lossTs = new Date(lossTime).toISOString(); // Query 1: Motion/activity events in 10 min before loss const [motionEvents] = await bq.query({ query: ` SELECT i.id, i.device_id, i.zone_id, i.event_type, i.occurred_at, TIMESTAMP_DIFF(@loss_time, i.occurred_at, MINUTE) AS mins_before_loss FROM \`tod_backoffice.incidents\` i WHERE i.facility_id = @facility_id AND i.occurred_at BETWEEN TIMESTAMP_SUB(@loss_time, INTERVAL 10 MINUTE) AND @loss_time AND i.event_type IN ( 'motion_detected', 'door_access', 'alarm_triggered', 'zone_entry' ) ORDER BY i.occurred_at DESC `, params: { facility_id: facilityId, loss_time: lossTs } }); // Query 2: Other gateways at same facility going offline within ±3 minutes const [simultaneousOutages] = await bq.query({ query: ` SELECT COUNT(*) AS count FROM \`sd_monitoring.gateway_outage_events\` WHERE facility_id = @facility_id AND gateway_id != @gateway_id AND detected_at BETWEEN TIMESTAMP_SUB(@loss_time, INTERVAL 3 MINUTE) AND TIMESTAMP_ADD(@loss_time, INTERVAL 3 MINUTE) `, params: { facility_id: facilityId, gateway_id: gatewayId, loss_time: lossTs } }); // Query 3: Gateway outage history (is this normal or unusual?) const [history] = await bq.query({ query: ` SELECT COUNT(*) AS outage_count_30d FROM \`sd_monitoring.gateway_outage_events\` WHERE gateway_id = @gateway_id AND detected_at > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY) AND status = 'CONFIRMED' `, params: { gateway_id: gatewayId } }); const lossHour = new Date(lossTime).getHours(); const isAfterHours = lossHour <= 6 || lossHour >= 22; return { motion_events_before_loss: motionEvents, motion_burst_count: motionEvents.filter(e => e.mins_before_loss <= 5).length, simultaneous_outages: simultaneousOutages[0].count, outage_count_30d: history[0].outage_count_30d, is_after_hours: isAfterHours, loss_hour: lossHour }; }

Step 3: Risk Classifier — Score the Threat Level

function classifyOutageRisk(context) { let score = 0; const signals = []; // Signal 1: Pre-outage motion burst (strongest indicator of intentional attack) if (context.motion_burst_count >= 3) { score += 35; signals.push(`${context.motion_burst_count} motion events in last 5 min before loss`); } else if (context.motion_burst_count >= 1) { score += 15; signals.push(`${context.motion_burst_count} motion event(s) before loss`); } // Signal 2: Multiple gateways offline simultaneously → jamming pattern if (context.simultaneous_outages >= 2) { score += 30; signals.push(`${context.simultaneous_outages + 1} gateways offline simultaneously — POSSIBLE JAMMING`); } else if (context.simultaneous_outages === 1) { score += 15; signals.push('2 gateways offline in same window — possible coordinated disruption'); } // Signal 3: After-hours outage (10pm–6am) if (context.is_after_hours) { score += 20; signals.push(`After-hours outage at ${context.loss_hour}:00 — elevated risk window`); } // Signal 4: No history of outages → unusual / first-time event if (context.outage_count_30d === 0) { score += 10; signals.push('No outages in past 30 days — gateway was stable'); } // Outage type classification from signal pattern let outage_type; if (context.simultaneous_outages >= 2) { outage_type = 'POSSIBLE_JAMMING'; } else if (context.simultaneous_outages === 1) { // Both gateways + facility-wide → more likely power/network than jamming outage_type = score >= 35 ? 'POSSIBLE_JAMMING' : 'NETWORK_OR_POWER'; } else if (context.motion_burst_count >= 3) { outage_type = 'SUSPICIOUS_TARGETED'; } else { outage_type = 'DEVICE_OR_NETWORK_FAILURE'; } const risk_level = score >= 60 ? 'CRITICAL' : score >= 35 ? 'ELEVATED' : score >= 15 ? 'SUSPICIOUS' : 'NORMAL'; return { score, risk_level, outage_type, signals, trigger_claude: score >= 15 }; }

Step 4: Acknowledgment & Escalation Logic

async function sendAlertWithEscalation(outageEvent, classification, fm, secondaryContacts) { const ackWindowMin = classification.risk_level === 'CRITICAL' ? 10 : classification.risk_level === 'ELEVATED' ? 15 : 20; // Build personalized alert message based on risk level const ackToken = await createAckToken(outageEvent.id, fm.id, ackWindowMin); const alertPayload = buildAlertPayload(outageEvent, classification, fm, ackToken); // Send via all channels simultaneously await Promise.all([ sendEmail(fm.email, alertPayload), // SendGrid template sendSMS(fm.phone, alertPayload.sms_body), // Twilio sendSlack(fm.slack_channel, alertPayload), // Slack webhook createBackofficeNotification(fm.user_id, alertPayload) // BackOffice API ]); // Log alert event await writeAlertLog({ outage_event_id: outageEvent.id, fm_id: fm.id, sent_at: new Date(), ack_token: ackToken, ack_deadline_min: ackWindowMin }); // Schedule escalation check setTimeout(async () => { const ack = await checkAckStatus(ackToken); if (!ack.acknowledged) { // FM did not respond — escalate to all secondary contacts for (const contact of secondaryContacts) { await Promise.all([ sendEmail(contact.email, buildEscalationPayload(outageEvent, classification, fm)), sendSMS(contact.phone, buildEscalationSMS(outageEvent, fm)) ]); } await writeEscalationLog({ outage_event_id: outageEvent.id, escalated_at: new Date() }); } }, ackWindowMin * 60 * 1000); }

Claude AI Deep Dive: What It Does & When

When Claude Triggers

  • Risk score ≥ 15 (SUSPICIOUS or higher) only
  • NORMAL outages: no Claude call — zero AI cost
  • ~$0.02–0.08 per SUSPICIOUS/ELEVATED/CRITICAL alert
  • Estimated: $3–8/month total across all facilities
  • Uses prompt caching — system prompt never re-sent

What Claude Receives

  • Gateway location, zone, facility name
  • Minutes silent and time of day
  • Number and types of motion events before loss
  • Simultaneous outage count (jamming indicator)
  • Gateway's 30-day outage history
  • Risk score and signals already computed
