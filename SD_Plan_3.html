AI Customer Health & Churn Predictor

Monitors 5 real-time signals per customer, generates a health score 0–100, and alerts the CS team with a specific intervention playbook before the customer cancels — turning reactive support into proactive retention.

Section 1

What is this? (Plain English)

No jargon. Read this first regardless of your background.

🚗
Think of it like a car dashboard warning light — before the engine fails, not after
Non-technical explanation

Right now, when an SD customer decides to cancel, the CS team usually finds out when it is too late — the customer has already made the decision. It's like only checking your oil level after the engine seizes.

This idea installs a "warning light" for every customer. The system watches 5 signals every day: Are their devices still online? Did they log into the portal this week? Are their incidents being resolved? Is their PMS sync working? Are their motion events trending up or down? It combines these into a single Health Score (0–100) per facility.

When a customer's score drops sharply — say from 76 down to 44 in one week — the system fires a Slack alert to the CS team: "Riverside Storage score dropped 32 points. Primary cause: PMS sync has been broken for 9 days. Recommended action: Fix the storEDGE integration today." The CS team gets the exact problem and the exact fix — not just a vague "customer seems unhappy".

👔
Why this protects more revenue than any new customer acquisition
Business case — 60 seconds

SD's subscription is $12/device/month flat. A facility with 60 Smart Units pays $720/month. If that customer churns, SD loses $720/month — and the cost to acquire a replacement customer is typically 3–5× higher than retaining an existing one.

The CS team currently reacts to problems after customers complain. This system predicts which customers are heading toward churn before they complain — giving CS a 2–4 week window to intervene. A single retained 60-device customer = $720/month × 12 months = $8,640/year kept.

The signals are already available in tod_backoffice — broken PMS sync, device offline rates, zero portal logins. No new data collection. This is purely about connecting the dots that already exist.

Step-by-Step Build Plan

7 steps — from raw signal collection to live CS alerts with Claude-generated intervention playbooks.

📊 Health Score Formula — 5 Weighted Signals (total: 100 points)
SignalWeightBarWhat it measuresData source
Device Uptime % 30 pts
% of active devices sending heartbeat in last 24 hrs devices table
Portal Login Frequency 25 pts
Number of distinct login days in last 30 days (0 = disengaged) user_sessions / Firebase
Task Resolution Rate 20 pts
% of created tasks resolved within 7 days (last 30 days) tasks table
PMS Sync Status 15 pts
Days since last successful PMS sync (broken sync = 0 pts) pms_integrations table
Incident Response Trend 10 pts
Month-over-month change in escalated incident rate incidents table
1
Data Layer
Write BigQuery SQL — collect all 5 signals per facility, daily

One query per signal. All run daily as part of the Cloud Run scoring job and return one row per facility.

-- Signal 1: Device uptime % (heartbeat in last 24 hrs) SELECT d.facility_id, COUNT(d.id) AS total_devices, COUNTIF(d.last_heartbeat >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)) AS online_devices, ROUND(SAFE_DIVIDE( COUNTIF(d.last_heartbeat >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)), COUNT(d.id)) * 100, 1) AS uptime_pct FROM `tod_backoffice.devices` d WHERE d.status = 'active' GROUP BY d.facility_id; -- Signal 2: Portal login frequency (distinct login days, last 30d) SELECT u.facility_id, COUNT(DISTINCT DATE(s.created_at)) AS login_days_last_30, DATE_DIFF(CURRENT_DATE(), DATE(MAX(s.created_at)), DAY) AS days_since_last_login FROM `tod_backoffice.user_sessions` s JOIN `tod_backoffice.users` u ON u.id = s.user_id WHERE s.created_at >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY) GROUP BY u.facility_id; -- Signal 3: Task resolution rate (last 30 days) SELECT facility_id, COUNT(*) AS total_tasks, COUNTIF(status = 'resolved') AS resolved_tasks, ROUND(SAFE_DIVIDE(COUNTIF(status = 'resolved'), COUNT(*)) * 100, 1) AS resolution_rate_pct FROM `tod_backoffice.tasks` WHERE created_at >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY) GROUP BY facility_id; -- Signal 4: PMS sync health SELECT facility_id, pms_type, last_sync_at, DATE_DIFF(CURRENT_DATE(), DATE(last_sync_at), DAY) AS days_since_sync, CASE WHEN DATE_DIFF(CURRENT_DATE(), DATE(last_sync_at), DAY) > 7 THEN 'broken' WHEN DATE_DIFF(CURRENT_DATE(), DATE(last_sync_at), DAY) > 3 THEN 'delayed' ELSE 'healthy' END AS sync_health FROM `tod_backoffice.pms_integrations` WHERE is_active = true;
2
Scoring Engine
Build the Health Score Engine — weighted score per facility, stored daily

A Cloud Run service that collects all 5 signal query results, applies the weighted formula, outputs a health_score (0–100) per facility, and writes a daily snapshot to BigQuery. The history table enables trend tracking and score delta calculation.

// health-scorer.js function calculateHealthScore(signals) { // Each signal scored 0–100 independently, then weighted const signal_scores = { device_uptime: signals.uptime_pct, // 0–100 direct portal_logins: Math.min(100, signals.login_days_last_30 * 5), // 20+ days = 100 task_resolution: signals.resolution_rate_pct, // 0–100 direct pms_sync: signals.days_since_sync <= 1 ? 100 : signals.days_since_sync <= 3 ? 70 : signals.days_since_sync <= 7 ? 30 : 0, incident_trend: signals.mom_escalation_delta <= 0 ? 100 : // improving or flat signals.mom_escalation_delta <= 10 ? 60 : 20 // worsening }; const weights = { device_uptime: 0.30, portal_logins: 0.25, task_resolution: 0.20, pms_sync: 0.15, incident_trend: 0.10 }; const health_score = Math.round( Object.keys(weights).reduce((sum, key) => sum + (signal_scores[key] * weights[key]), 0) ); // Find the worst signal — this drives Claude's intervention const lowest_signal = Object.entries(signal_scores) .sort(([, a], [, b]) => a - b)[0][0]; return { health_score, signal_scores, lowest_signal }; } // Daily job: score all facilities, store snapshot, detect drops async function runDailyScoring() { const facilities = await getActiveFacilities(); for (const facility of facilities) { const signals = await collectSignals(facility.id); const result = calculateHealthScore(signals); const previous = await getScoreFromDaysAgo(facility.id, 7); const delta = result.health_score - (previous?.health_score ?? result.health_score); // Store daily snapshot to BigQuery history table await writeSnapshot(facility.id, result, delta); // Trigger Claude alert if score dropped significantly if (delta <= -15 || result.health_score < 45) { await triggerIntervention(facility, result, delta); } } }
3
AI Layer — Claude
Integrate Claude API — diagnose the drop and write a specific intervention playbook

Claude is called only when a score drops ≥15 points in 7 days, or falls below 45. It reads the signal breakdown, identifies the primary cause, and writes a specific actionable recommendation for the CS team — not a generic "reach out to customer" message.

// claude-health-advisor.js async function generateIntervention(facility, scoreResult, delta) { const payload = { facility_name: facility.name, current_score: scoreResult.health_score, score_delta_7d: delta, // e.g. -32 (dropped 32 pts in 7 days) signal_scores: scoreResult.signal_scores, lowest_signal: scoreResult.lowest_signal, smart_unit_count: facility.smart_unit_count, monthly_sub_usd: facility.smart_unit_count * 12, // e.g. $720/mo pms_type: facility.pms_type // e.g. 'storEDGE' }; const response = await client.messages.create({ model: "claude-sonnet-4-6", max_tokens: 500, system: [{ type: "text", text: `You are a customer success analyst at Storage Defender. A customer's health score has dropped. Diagnose the primary cause from the signal data provided and write a specific, actionable intervention for the CS team to take TODAY. Be direct — name the exact signal that is failing and give a concrete next step. 2–3 short paragraphs. Always mention the customer's monthly subscription value so the CS team knows what retention is worth. Never invent data.`, cache_control: { type: "ephemeral" } }], messages: [{ role: "user", content: JSON.stringify(payload, null, 2) }] }); return response.content[0].text; }
4
Slack Alerting
Send real-time Slack alerts to CS channel when a score drops

When the intervention is triggered, post a formatted alert to the CS Slack channel. The message includes: facility name, health score, 7-day delta, the specific failing signal, Claude's recommendation, and a link to the CS dashboard.

// slack-alert.js async function postHealthAlert(facility, scoreResult, delta, claudeAdvice) { const scoreColour = scoreResult.health_score >= 80 ? '#40c060' : scoreResult.health_score >= 60 ? '#e0c020' : scoreResult.health_score >= 40 ? '#e07020' : '#e03040'; await slackWebhook.send({ text: `⚠️ Customer health drop: *${facility.name}*`, attachments: [{ color: scoreColour, fields: [ { title: 'Health Score', value: `${scoreResult.health_score}/100`, short: true }, { title: '7-Day Change', value: `${delta} pts`, short: true }, { title: 'Failing Signal', value: scoreResult.lowest_signal, short: true }, { title: 'Monthly Sub', value: `$${facility.smart_unit_count * 12}/mo`, short: true }, { title: 'AI Recommendation', value: claudeAdvice } ] }] }); }
💡

Why Slack first? SD's CS team already uses Slack daily. A Slack alert requires zero new tooling — just a webhook URL. The Looker Studio dashboard is for long-term tracking; Slack is for same-day action.

5
CS Dashboard
Build Looker Studio dashboard — all customers ranked by health score + trend

A Looker Studio dashboard connected directly to the BigQuery health_scores history table. The CS team can view all facilities, filter by score band (Critical / At Risk / Needs Attention / Healthy), and see the 30-day trend per customer.

📊

Setup time: ~4 hours once the BigQuery history table is populated. Connect Looker Studio, add date range filter, create score band chart, add trend sparkline per row. CS manager gets a Monday morning view of every at-risk account.

6
Weekly Digest
Send weekly CS manager digest — top 10 at-risk accounts with trends

Every Monday morning, send an automated email digest to the CS manager listing the 10 lowest-scoring accounts, their week-over-week delta, and the primary failing signal for each. Uses SendGrid with a simple HTML template — no Claude needed for the digest (just templated data).

// weekly-digest.js (no Claude needed — templated data only) const atRiskAccounts = await bigquery.query(` SELECT facility_name, health_score, delta_7d, lowest_signal, smart_unit_count * 12 AS monthly_sub_usd FROM tod_backoffice.health_scores WHERE DATE(scored_at) = CURRENT_DATE() ORDER BY health_score ASC LIMIT 10 `); await sendgrid.send({ to: CS_MANAGER_EMAIL, subject: `SD Weekly Health Report — ${atRiskAccounts.filter(r => r.health_score < 60).length} accounts need attention`, html: digestTemplate({ accounts: atRiskAccounts }) });

Testing & Validation
Backfill 30 days of history, validate scores, pilot with CS team

Before going live, backfill 30 days of historical score data by running the scoring engine against past BigQuery snapshots. This gives the CS team an immediate trend view from day one — not a blank dashboard.

Have the CS team manually review the bottom 10 scored facilities and confirm: does the score match their intuition about which customers are actually struggling? Iterate on signal weights if needed.

Section 4

Claude AI — Deep Dive

Claude is used only when needed — triggered by score drops, not on every daily run. This keeps costs minimal and impact maximal.

🤖

Claude Sonnet 4.6 — Anthropic API

Model ID: claude-sonnet-4-6  |  SDK: @anthropic-ai/sdk  |  Called only on score drops (≥15 pts or score <45)
What Claude Does Here
  • Reads the signal score breakdown (which signals are low)
  • Identifies the primary root cause of the score drop
  • Writes a specific CS intervention (not generic)
  • Names the exact action: "fix storEDGE sync", "schedule training", etc.
  • Includes the customer's monthly subscription value ($12 × devices)
Why Only on Score Drops?
  • Healthy customers don't need intervention — calling Claude daily for all 200+ facilities wastes budget
  • Triggered-only approach: ~10–20 alerts/day across entire fleet
  • Cost drops from ~$40/month (daily all) to ~$3–5/month (triggered only)
  • Alerts feel more urgent when they're selective, not noise
Cost Estimate (per month)
  • ~15 score drop events/day × 30 days = 450 API calls/month
  • ~500 output tokens per intervention
  • System prompt cached per batch (5-minute TTL)
  • Estimated: ~$3–5 USD/month for all alerts
  • Scales with fleet size — still negligible vs retention revenue
What Claude Must NOT Do
  • Must not invent churn probability % (not enough data for this yet)
  • Must not invent revenue figures — only use devices × $12
  • Must not be alarmist — tone is "here is a specific thing to fix" not "this customer is leaving"
  • Must cite the exact failing signal so CS can verify independently
📝 Sample Claude Output — what appears in the CS Slack alert

"Riverside Storage health score dropped 32 points this week (76 → 44). The primary cause is a broken PMS sync — storEDGE last synced 9 days ago, which means tenant move-in/move-out data is stale and the facility manager may already be noticing data discrepancies.

Secondary signal: portal logins dropped to 2 days this month (down from 14 last month) — this is consistent with a frustrated customer who stops using the product when it stops syncing correctly.

Recommended action: Contact the facility manager today and offer to fix the storEDGE integration sync — this is typically a 15-minute fix. Riverside Storage is a $720/month account (60 devices × $12). Resolving the sync issue should restore their score above 70 within 48 hours."

🗂️ Intervention Playbook — Claude recommends based on the lowest signal
Low Device Uptime (<70%)
Trigger: uptime_pct drops below 70%
Hardware connectivity issue. Escalate to SD Support team to investigate offline devices. Offer the facility manager a same-day fix call. Check gateway status in the BackOffice device panel.
Low Portal Logins (<5 days/month)
Trigger: login_days_last_30 < 5
Disengaged customer. Send the AI Monthly Value Report (Idea #1) immediately. Schedule a 30-min training call. CS team to check if the facility manager changed role or left the company.
Low Task Resolution (<50%)
Trigger: resolution_rate_pct < 50%
Incidents piling up unresolved — customer may feel overwhelmed or undertrained. Offer an incident response workflow review. Check if the escalation matrix is configured correctly in Manage Facility.
Broken PMS Sync (>7 days)
Trigger: days_since_sync > 7
Silent churn signal — stale tenant data causes data accuracy complaints. Fix the PMS integration (storEDGE / SiteLink / SSM) — typically a 15-minute config fix. Most common cause: API key expired or webhook endpoint changed.

Section 7

AI Tool Options

Health scoring itself is rule-based. Claude is used only for generating intervention text on score drops. Here are the options.

⭐ Recommended
🤖

Claude Sonnet 4.6

Best at diagnosing complex multi-signal situations and writing concise, specific, actionable text.

  • Triggered-only = ~$3–5/month (not daily cost)
  • Understands nuance: "low PMS sync + low logins = very different from low logins alone"
  • Prompt caching for batch triggers
  • SD already has Anthropic account
  • Easiest to tune via system prompt
📋

Rule-Based Templates

No AI — use if-else logic to pick a pre-written playbook based on the lowest signal.

  • Zero API cost
  • Faster to build for pilot
  • Less context-aware — misses compound signals
  • Good fallback if API key is delayed
  • Can layer Claude on top in v2
🔵

Google Gemini (Vertex AI)

Keeps everything within GCP. Good backup if Anthropic access is delayed.

  • Native GCP — no external vendor
  • Free tier available for low volume
  • More Vertex AI setup complexity
  • Slightly weaker at structured instruction following
  • Viable option for cost-sensitive pilot
